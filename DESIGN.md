# Design

Shared library crate for the PostPerfection suite. dcpdoctor, dcpwizard, and imfwizard depend on it by path; anything needed by more than one app lives here. Depends on asdcplib-rs (git) for MXF I/O. dcpdoctor-wasm deliberately does not use postkit (no-std-io rewrites in dcpdoctor-parse/-imf).

## Modules (67 in lib.rs)

Packaging and formats:
- certificate: X.509 chains, KDM creation/rewrap, trust management. KDM content keys are caller-supplied (from the DCP's keys file) so the KDM unlocks the actual encrypted essence, falling back to a fresh MDIK when none are given. One certificate thumbprint throughout, the base64 ST 430-2 value (SHA-1 over the DER TBSCertificate) that a KDM lists; the trusted-device store names its files by the hex spelling of that same digest and migrates older stores on access. `KdmFormulation` picks the ISDCF formulation: it emits ContentAuthenticator (the signer leaf's thumbprint) for `dci-any`/`dci-specific` and rejects a `device_cert_files` its formulation would silently discard
- xmldsig: enveloped XML-DSig sign/verify, SMPTE 430-3 profile (xmlsec1-cross-checked in tests). `SignatureProfile` picks rsa-sha256 or rsa-sha1 at sign time via `sign_document_enveloped_as` (`sign_document_enveloped` stays rsa-sha256); verification reads the declared DigestMethod/SignatureMethod and dispatches on them (sha1/256/384/512, rsa-sha1/256/384/512), so real SHA-1-signed Interop DCPs verify. Unknown algorithms fail loud. `dcp_signer_element` builds the CPL/PKL `Signer` (ds:KeyInfoType wrapping X509Data, per real ECL packages), a different shape from the KDM's ETM Signer. `strip_signature` drops the ds:Signature and the Signer beside it, whatever prefix they carry, for anything that rewrites a signed document: a signature left over edited bytes reads as tampering rather than as an unsigned package
- packaging: shared DCP/IMF CPL, PKL and ASSETMAP XML writers, plus the one public `escape_xml` and namespace constants. Output is SMPTE-XSD-valid: writers emit elements in ST 429-7/8/9 order and include the required IssueDate/Issuer/ContentVersion/RatingList; AssetMap orders its metadata by namespace (SMPTE vs Interop). DcpCpl reels carry an optional picture/sound KeyId, emitted when the essence is encrypted. DcpCpl also carries an optional ContentVersion LabelText (the title when absent) and a list of ratings, written as Agency/Label pairs in a RatingList that stays empty and byte-identical when no ratings are given. ImfCpl carries optional MaxCLL/MaxFALL, emitted as app2e ExtensionProperties beside ApplicationIdentification (ST 2067-21 puts these in the CPL, not the MXF descriptor), byte-identical output when absent
- mxf_wrap: J2K/PCM/timed-text/Atmos wrapping for DCP and AS-02 via asdcplib-rs, with optional AES-128 essence encryption at wrap time (J2K/PCM); the content key stays out of any serialized form and is redacted in Debug. A J2K picture wrap takes only the codestreams its standard can carry: a DCI cinema Rsiz into AS-02 and an IMF Rsiz into AS-DCP are both refused by Rsiz, because the first carries X'Y'Z' samples and the second RGB, and neither reader is told which. An AS-02 J2K wrap also needs `hdr` to set ColorPrimaries or TransferCharacteristic, which ST 2067-21 puts on the RGBA essence descriptor and nothing else writes; `rec709_sdr_picture_colour()` is the pair an SDR App 2E picture signals. The picture descriptor carries the first frame's parsed codestream header, so the JPEG2000 sub-descriptor and the PictureEssenceCoding label asdcplib derives from it describe the essence that was wrapped. A timed-text wrap reads the document's own id out of the XML (DCST `<Id>`, Interop `SubtitleID` as an element or a root attribute) and writes it as the ResourceID ST 429-5 asks for, keeping the track file's `asset_uuid` distinct from it. A document with no id is refused rather than wrapped under an invented one. The essence duration comes from the last cue unless `timed_text_duration_frames` names it, which is how a caller gives a reel's subtitle asset the reel's length; a cue ending past a named duration is refused. `mxf_wrap` itself reads every input file into memory, so the J2K picture path has a second form for essence that does not exist yet: `IncrementalJ2kWrap` takes one codestream at a time, opening asdcplib on the first frame (the descriptor comes from its codestream header) and passing 0 for ContainerDuration, which asdcplib overwrites with the frames actually written when it rewrites the header partition at finalize. `OverlappedJ2kWrap` runs one of those on its own thread behind a `FrameReorderBuffer`, so an encoder can hand it frames in completion order; only `finish` leaves an MXF behind, and it refuses a frame count other than the one the encoder reports, because an MXF with no footer or a short one cannot be read at all. Everything else stays sequential: stereoscopic interleaves two eyes per frame, and sound, Atmos and timed text have no frame-by-frame producer
- cpl_xml: string-level CPL/OPL XML tag helpers. `replace_tag` is `write_tag` that reports whether the element was there, so a caller can refuse an edit that would silently go missing
- cpl_annotation, metadata_edit: CPL/OPL field read/write. Both work on one CPL file and leave the package around it alone, which is what separates them from package_edit. `metadata_edit::write_metadata` picks the annotation element out of package_edit's `CplVocabulary`, so the two modules cannot disagree about what ST 2067-3 calls it
- package_edit: retitle or re-annotate a package that is already written, DCP or IMP, without re-wrapping essence. `edit_package` gives the CPL a new composition id (a changed CPL is a different composition), rewrites the fields asked for, then repoints the PKL entry (id, new hash and size) and the ASSETMAP entry (id and Path) at it. Essence files keep their asset ids and their bytes. A `CplVocabulary` per standard is the only place the two formats differ: ST 429-7 names the title `ContentTitleText` and the annotation `AnnotationText` and may carry a ST 429-16 `meta:FullContentTitleText` to keep consistent, ST 2067-3 names them `ContentTitle` and `Annotation` and has no metadata title. Documents are found by root element, not by file name, so an Interop `ASSETMAP` with no extension and a PKL under any name still resolve. An encrypted package is refused: a KDM authorises its keys for one named composition id, and this mints a new one. A signed document is rewritten unsigned and named in `unsigned_documents`, since the signature no longer covers the bytes. Setting a field the CPL does not have is an error rather than a silent no-op
- mca: ST 377-4 channel labels, soundfield presets, MCA XML
- j2k: J2K codestream header parsing, DCI bitrate analysis over a sequence of codestream files, and single-frame extraction from a picture MXF (`read_mxf_j2k_frame`, `parse_j2k_from_mxf`). `MxfBitrateStats` is the shape a per-frame measurement reports; measuring an MXF is not done here, because the only consumer (dcpdoctor) has to reach essence this reader cannot open. It also composes an IMF Rsiz, which is the profile base (0x0400 2K, 0x0500 4K, 0x0600 8K) with the sub level and then the main level in the low byte: `ImfProfile::for_raster` picks the profile from the picture size, `imf_levels` reads the main level off the megasamples per second (width x height x 3 x fps) and the sub level off the megabits per second, and `imf_rsiz` puts them together. Table A.53 pairs the two, so a sub level of 2 or more raises the main level to two above it, which is why 2048x1080 at 24 fps and 250 Mb/s is main level 4 rather than the 3 its sample rate alone asks for. A raster or a rate past the top level is refused rather than clamped, and a grok-ffi test asserts both tables still equal grok's own constants
- hash: SHA-1/SHA-256 file hashing
- dcdm: DCDM creation; Rec.709 to X'Y'Z' via gamma 2.2 + 48/52.37 companding + 2.6 gamma (matching colour::rgb_to_xyz_inplace and libdcp/DoM/grok), 12/16-bit TIFF. The per-pixel maths is `colour::DcdmTransform`, so the file pipeline and the encoder cannot drift apart; this module adds the name parsing and the P3-D65 target

Encoding:
- encode: J2K encode orchestration (detection, the ffmpeg stream encode, the TIFF sequence encode, progress). `StreamEncodeOptions.source_colour` is `DisplayRgb`, `DisplayRgbIn(space)`, `DciLut(path)`, `AlreadyPq` or `KeepRgb` plus an optional `codestream_byte_cap`: grok gets `--xyz` if and only if the variant applies the XYZ transform and the LUT runs in the same ffmpeg pass, so XYZ-transformed frames can never be labelled PQ. `DisplayRgbIn` is the P3/Rec.2020 route grok's own transform does not model: it carries a `DcdmTransform` into `CompressParams.source_preparation.colour_transform`, which the encoder threads run over each packed 16-bit frame with grok's transform off. The J2K branch refuses it, since nothing can be converted once the frames are compressed. `StreamEncodeOptions.quality_psnr` swaps grok's rate allocation for a PSNR target, and since grok ignores `max_cs_size` under quality allocation, a frame whose codestream exceeds the byte cap is compressed again by rate at `raw_frame_bytes / cap` on the encoder thread, leaving the writer's size check as the last line of defence. `source_preparation` also carries the subtitle burn, and applies it first: text is authored in display RGB, so it has to be composited before any conversion to X'Y'Z', and the two steps share one function so the order cannot be reversed. Every stream decode also carries a `split` branch running `blackdetect` and `freezedetect`, whose black and frozen runs come back as `EncodeResult.picture_findings` in output frame numbers: the branch exists because neither filter accepts rgb48be, so in the main chain ffmpeg would round trip every frame through yuv444p16le before the compressor saw it. `DecodeSource::ImageList` takes an image sequence through ffmpeg's concat demuxer, so it reaches the same per-frame hooks a video does. `stream_encode_inprocess_with_mxf_feed` is the same encode with a picture MXF being written alongside it: the codestream goes to the feed once it is on disk, so the .j2c files stay exactly what they were. `StreamEncodeOptions.rsiz` is the profile the codestreams declare and defaults to cinema 2K, so an IMF encode is that field carrying `j2k::imf_rsiz` and `source_colour` set to `KeepRgb`, the variant that compresses display RGB untouched for picture whose descriptor names the colour. The same pair reaches every encoder a caller enters by: `EncodeRunOptions.rsiz` forwards it into the `StreamEncodeOptions` the pipeline builds, which `encode_tiff_sequence_inprocess` takes as well, and `StillHold.rsiz` sets `CompressParams.profile` for a held picture. `encode_loaded_frames` is the one encoder that reads no ffmpeg pipe: a small pool of loader threads (a quarter of the cores, at most four), each holding the loader `open_loader` gave it so a loader can own an MXF reader, hands frames over a bounded channel to the pipeline's producer while the encoder threads keep every core. A frame that fails to load stops the loaders, and the run fails with that error once the frames already handed over are compressed. `DciLut` is refused there, since that LUT is an ffmpeg filter. `encode_tiff_sequence_inprocess` is that encoder with `grok::load_tiff` and `TiffFrame::into_rgb48_frame` as the loader, which shifts 8, 12 or 16-bit samples up to the packed 16-bit frame the encoder threads take, so the burn, the colour transform, the profile, the byte cap and the MXF feed all work on stills exactly as on decoded video. A 12-bit still shifted up by four and reduced by four again lands on its own samples. `choose_pipe_format` decides what ffmpeg writes to the pipe from the run's own options and from `probe::probe_pixel_format`: the source's own planar YUV when grok's accelerator plugin is on and nothing between the decoder and the compressor reads the samples, and packed 16-bit RGB otherwise, which is every run with a subtitle burn, postkit's own colour transform, the HDR-to-DCI LUT, a filter chain that changes the pixel format or the colour, or a PSNR target, since a frame over the byte cap has to be compressed again by rate. `pipe_format_for_run` is that choice plus the plugin's own answer: it asks about the planar YUV shape and, for a run left on packed RGB, about an interleaved `rgb48le` batch, each by beginning a batch with the run's compression parameters and ending it with no frame submitted. Each ask starts a batch, so a run asks at most twice and only about a source everything else already allows through, and a declined ask leaves the format it would have replaced. `PipeFormat::PackedRgb` carries the byte order that answer chose, so `RawFrame::Packed` reaches the encoder threads as `rgb48le` when the plugin takes the interleaved buffer and `rgb48be` when postkit deinterleaves it itself. `decode_filter_chain` builds the chain the decode runs, the picture filters with the detection branch split off them, and inserts `format=gbrp16le` ahead of every other filter when the pipe is packed RGB and `probe_pixel_format` read one of the 8-bit YUV formats `is_eight_bit_yuv_pixel_format` names, since swscale converts one of those straight to rgb48 at 8 bits and lands about two codes of 255 off: the conversion goes first so the geometry work, the decode LUT and the packing to rgb48 all run at 16 bits, and the pipe format is decided on the chain before the insertion so it cannot move that decision. `encode_tiff_sequence_inprocess` asks the same question once, at the first still's raster, and `TiffFrame::into_rgb48_frame` packs every still in the order it answered.
- grok: `load_tiff` (8, 16-bit through the tiff crate, 12-bit unpacked from the strips by hand, rows padded to a byte) and `write_tiff_rgb`, its inverse, the uncompressed RGB TIFF an export writes at the codestream's own precision. No grok command line tool is looked up or run anywhere: encoding and decoding are the linked library
- grok_encoder: in-process Grok J2K encoder (FFI, feature-gated behind `grok-ffi`). Producer, N encoder threads and one writer thread, which writes `frame_{index:08}.j2c` as frames arrive and, given an `encode_pipeline_with_mxf_feed` feed, hands each one on to an MXF wrap after it is on disk. Frames reach the feed in completion order, which the wrap end reorders; a feed that has stopped fails the encode, which is how a wrap error gets out. The writer also sizes each codestream against an optional `codestream_byte_cap` as it lands, so a bitrate over the cap fails at the first frame that shows it instead of after the last one; recording that error closes the input queue, which is what releases a producer blocked on a full queue after the encoder threads have stopped. The producer may stop short of `total_frames` (a decoder that ends early, a loader that fails), so the drain waits on the frames actually handed over rather than on the total, or it would never return. `CompressParams.edit_rate` is the exact rate as a `FrameRate`, because `encode_video_pipeline_resumable` converts blackdetect's and freezedetect's seconds into frame numbers with it and 24 instead of 24000/1001 puts the end of a 25 second black head a frame late. grok itself is handed the rounded whole rate, which is all DCI rate control has: `grok_frame_rate` rounds once for `cparams.framerate`. An IMF `CompressParams.profile` changes what the encoder threads hand grok: cinema profiles get the samples at their own precision, because grok reduces them to 12 bits itself as part of its X'Y'Z' transform, while an IMF codestream is written at whatever precision it is given, so the encoder shifts each sample down to 12 bits and declares `comp.prec` 12. An IMF profile with `apply_xyz_transform` set is refused, since that essence is RGB, and so is a frame below 12 bits. Everything else an IMF profile requires (32x32 code blocks, CPRL, one layer, 9-7) is grok's own `setImfParams`. With grok's accelerator plugin switched on, the encode runs as one batch through the plugin's pipeline instead of a `grk_compress` per frame: the first frame fixes the batch's width, height and precision, the encoder threads run the subtitle burn and the colour transform as before and then submit, which blocks while the plugin's pipeline is full, and the plugin's own threads hand each code stream to the same writer thread, out of order, which is the order the writer already took. `grk_plugin_batch_memory_end` runs after the encoder threads are joined and before the drain, because the tail of the pipeline only completes there. A frame shape or a set of parameters the plugin declines puts the whole run on the CPU path with a log line, and a device failure fails the run. An encode with `quality_psnr` stays on the CPU path, since a frame over the byte cap has to be compressed again by rate and the batch has no way to re-encode one frame. Decoding still routes per call. The batch takes three frame layouts. A planar RGB frame is the `int32` image grok's own compress takes, deinterleaved from `rgb48be` on the encoder threads. A `PlanarYuv` frame is the source's three planes as ffmpeg's rawvideo muxer wrote them, handed over as a grok image whose components point straight into the frame with `owns_data` false, `GRK_INT_8` at 8 bits and `GRK_INT_16` at 10, and the plugin upsamples the chroma and converts the colour on the device. A little-endian `Packed` frame goes over as `GRK_SOURCE_RGB48LE`, one interleaved buffer with the image's first component pointing at it, `comps[0].stride` the row pitch in 16-bit samples and the other two components carrying no data, and `info.source_prec` the frame's own 16 bits against an `info.prec` of 12. grok copies the frame inside submit either way, so the buffer can be dropped as soon as that call returns. `plugin_takes_frame` is the begin-and-end question the pipe format choice asks with a frame that carries a shape and no bytes: the plugin declines a 16-bit source written at 12 bits with the X'Y'Z' transform off, planar and interleaved alike, so the IMF profile and the already-converted cinema colours stay on packed big-endian RGB.
- picture_processing: what happens to the source picture while it decodes. `PictureProcessing` (per-side `Crop`, `Rotation`, horizontal and vertical flip, deinterlace, denoise, optional `Fit`) resolves to a `PicturePlan` by pure arithmetic first, so the sizes a GUI shows and the sizes ffmpeg really produces come from one place, and only then to `-vf` items. The order is fixed: yadif before the fps filter, so fields become frames before any rate conversion, hqdn3d after it, then `format=gbrp16le` ahead of every geometry step, so a crop offset on a chroma-subsampled source is honoured exactly and pad black is exact zero, then crop, transpose, hflip, vflip, scale (lanczos) and pad, with the source colour's `lut3d` last. Identity steps emit nothing at all. `Fit` scales the processed picture into a box with its aspect kept and centres it on a larger raster with black around it, which is how a source whose raster is not the encode raster reaches one. The plan's output size is the frame size both stream encoders slice out of ffmpeg's pipe and the raster the codestream declares, and `PicturePlan::describe` is the one-line form for a log or a crop indicator. `detect_black_borders` seeks a few frames spread over the content, runs cropdetect on each and unions the content rectangles, so a frame that happens to be dark cannot crop away picture another frame has Deliberately out: arbitrary rotation angles, anamorphic desqueeze, field-rate deinterlacing (yadif emits one frame per frame) and border detection during the encode, which stays a separate pass a caller runs first because it seeks and decodes frames of its own.
- pipeline: shared encode workflow used by the wizard GUIs. A TIFF sequence is read by postkit's own loader threads and goes to the in-process encoder as packed 16-bit frames, unless a non-identity `picture` needs ffmpeg's filter chain. Every other still format (DPX, EXR, BMP, PNG, JPEG) reaches ffmpeg through the concat demuxer, one frame period per still. `reject_unsupported_colour_path` hangs on the branch actually taken: the TIFF branch takes every colour but `DciLut`, which is an ffmpeg filter. J2K input refuses picture processing outright, and the edit rate travels as the rational `FrameRate` from `EncodeRunOptions` to ffmpeg's `fps` filter and the concat list, so 24000/1001 stays exact end to end. `read_source_at` is the other half of the rate story: it reaches ffmpeg as an input `-r` before `-i`, which regenerates constant-rate timestamps so the `fps` filter of the same rate passes every frame through untouched. That is the 23.976-to-24 conform, where the picture plays 0.1% faster rather than gaining a duplicated frame every 1001, and the caller pulls the sound up by the same 1000/1001. It is video only, since a concat list already holds each still for one frame period. `run_encode_and_wrap_picture` is `run_encode_with_options` with the picture MXF wrapped as the encode runs rather than after it, so no caller waits for the encode to end and then reads the whole J2K directory back. It refuses a J2K sequence, which is never encoded and so hands postkit no codestream, instead of quietly wrapping nothing, and a cancel or a failure on either side deletes the part-written MXF and leaves the codestreams that finished
- prores: ProRes probe and extraction arg builders

Timeline and ingest:
- conform: CMX 3600 EDL, FCP7 xmeml, FCP X fcpxml and OTIO import, reel assembly (AAF rejected loudly here, dcpwizard routes AAF through libaaf before postkit). The fcpxml path builds a document tree and places clips recursively (child record time is parent record zero plus child offset minus parent start, visible range intersected with the parent's slice), so connected clips in lanes, compound clips, nested and sync clips, connected storylines and clips attached to gaps all resolve. The OTIO path parses the JSON with serde_json, takes the sequence rate from `global_start_time` (else the first source_range rate), accumulates per-track record positions, and names reels by the media target_url basename. `EditEvent.lane` orders flattened lanes, `EditEvent.gain_factor` carries a constant clip gain multiplier for formats that have one (AAF today), and `Timeline.skipped` names every construct with no source clip behind it (titles, captions, generators, transitions, multicam, auditions), nothing is dropped silently
- edl_import: standalone EDL/FCP XML parsing
- otioz_import: OTIOZ bundle extraction (zip walk, media extraction); the timeline inside parses through conform's OTIO parser
- ingest: camera format detection (ARRI/RED/BRAW/CRM magic bytes); transcodes ffmpeg-decodable inputs (ProRes, DNxHR) and rejects true camera RAW loudly (stock ffmpeg cannot decode it)
- timecode: SMPTE timecode/framerate math (single home for it)
- subtitle_retime: TTML/SRT framerate retiming, plus a standalone SRT cue parser
- subtitle_formats: input parsers that all yield a common `StyledCue` (SRT-style ms timing, styled text runs with italic/bold/underline/colour, optional horizontal align / vertical anchor / vertical position percent, optional bitmap image path), with `to_srt_cue` for the lossless-to-plain `SrtCue` path. Covers ASS/SSA (per-style + inline `\i \b \u \an`, unsupported override tags returned as warnings rather than dropped), PAC (Latin codepage, byte map and timecode decode ported from Subtitle Edit's Pac.cs; non-Latin codepages fail loud), MKS/Matroska (ffprobe lists streams and ffmpeg extracts the chosen SRT/ASS one, no EBML parser; fails loud on missing ffmpeg or no subtitle stream), FCPXML caption/title with exact rational offset/duration timing, and Interop DCSubtitle XML that references PNG bitmap subs (each PNG resolved relative to the XML and validated for existence + magic). Submodules: `bidi` (a pure logical-to-visual reorder for RTL subtitles, Arabic presentation-form shaping via ar-reshaper then Unicode bidi reorder per line, plus `has_rtl` for whether a line needs that reorder at all, which the bidi algorithm answers rather than a list of script ranges) and `wrap` (max-column line wrapping that breaks on whitespace, keeps an overlong word whole, and preserves styled-run boundaries; plain-string and `StyledCue` forms)
- subtitle_raster: burnt-in subtitles. `SubtitleRasterizer` shapes `StyledCue`s with cosmic-text (harfrust shaping, unicode-bidi reordering, fontdb system-font fallback or a supplied .ttf/.otf) and swash-rasterises them to positioned RGBA bitmaps, honouring per-run bold/italic/underline/colour and per-cue align/valign/vposition; a bitmap cue decodes its PNG and scales it to fit instead. `composite_rgb48` alpha-blends the bitmaps onto a packed rgb48 frame in integer math, clipping to the frame. `SubtitleBurn` binds a cue list to a frame rate for the encoder, caching the last render because the active cue set changes a few times a second at most; `active_cues` names the cues on one frame, so a caller holding a still can encode once per cue change. Nothing here knows about the encoder. `BurnStyle` also carries the appearance settings ffmpeg's `subtitles` filter cannot reach, named after their SMPTE subtitle counterparts so a burnt track and a packaged track can be asked for the same way: `effect` (`None`, `Outline`, `Shadow`, defaulting to the shadow the packaged XML defaults to) with `effect_colour` and `outline_width_ratio`, `line_height_ratio`, `x_scale`/`y_scale`, and `fade_up_ms`/`fade_down_ms`. The effect is a second pass of the same shaped glyphs in the effect colour, dilated or offset under the text, so bidi order, fallback and italics carry through it. `y_scale` scales the text height while `x_scale` bilinearly resamples the finished raster, since cosmic-text shapes at one size in both axes. A fade is an 8-bit alpha multiplier baked into the rendered pixels and included in the render cache key, so a cue mid-fade re-renders per frame and one at full strength still hits the cache. Bitmap cues fade but take no effect or scale. The flag-value parsing for that appearance is here too, `Rgba::parse_hex` for colours, `parse_burn_effect` for effect names and `BurnStyleOverrides` for the percent sizes and their ranges, including the line height multiple and the margin off the anchored edge, so dcpwizard and imfwizard read the same flags the same way. `find_system_sans_font` hands back a sans-serif font file off the same fontdb scan, preferring Liberation Sans then DejaVu Sans then whatever the generic sans-serif resolves to, so a packager can embed a font when the caller named none. Only a whole file on disk qualifies, because the subsetter reads the first face of whatever bytes it gets
- font_subset: TTF/OTF glyph subsetting to a code-point set via allsorts (`subset_font(bytes, chars)`), emitting a usable standalone OpenType font that keeps its cmap (Minimal profile + Unicode cmap), so an embedded subtitle font fits the SMPTE/interop 640 KB limit. Chars resolve to glyph ids through the font's own cmap

Media tooling (ffmpeg/external-tool wrappers). These are honest about their limits:
- colour: `parse_colour_space` reads a space's name off a command line, taking every spelling either wizard ever took. Rec.709/P3/Rec.2020 via ffmpeg; XYZ/ACES/ACEScg/LogC require a LUT or the dcdm path, else rejected. DCPwizard uses this LUT path for required HDR-to-DCI transforms; generic HDR tone mapping stays an explicit caller choice. `DcdmTransform` is the in-memory source RGB to DCI X'Y'Z' encode, built once per run and applied per frame (`frame_rgb48le`, `frame_rgb48_inplace`, `pixel`): linearize with the source space's own curve, matrix into XYZ, scale by the DCI companding coefficient 48/52.37, then 2.6 gamma. Rec.709 (gamma 2.2, sRGB/D65 matrix) matches libdcp's `rec709_to_xyz` + `rgb_xyz.cc` (DoM parity) and grok's `applyXYZTransform`, so the encode path (grok FFI) and pad-colour frames agree; P3 (gamma 2.6, DCI white) and Rec.2020 (gamma 2.4, D65) are the spaces grok cannot convert itself. LogC decodes with ARRI's LogC3 EI 800 curve and the ALEXA Wide Gamut D65 matrix, and scene linear above 1.0 clips to white. ACES and ACEScg are refused here: they are scene-referred, so no 3x3 matrix reaches X'Y'Z' from them. `rgb_to_xyz_inplace` is the Rec.709 one-shot form of it. Also the display transform `XyzToSrgb`: the inverse of the DCDM encode (code/4095 → ^2.6 → Y-scale to DCI ref white → XYZ→sRGB → sRGB OETF), built once as LUTs + a 3x3 matrix. It adapts no illuminant: a DCDM stores absolute XYZ without recording its neutral, and the encode above leaves a Rec.709 or P3-D65 master's neutral at D65, so adapting here tinted every DCP built from one. Rec.709 through the encode and back returns within a code or two, and a picture graded against DCI white renders green, which is what it measures. `XyzToIcc` (`icc` feature) routes X'Y'Z' → a monitor ICC through littleCMS with a selectable intent, adapting D65 to the D50 PCS
- preview: two paths. Plain files still go through ffplay (real frame rate, errors on options it can't fulfil). The DCP-native path resolves a DCP dir/CPL/MXF to the picture essence, decrypts it in Rust when encrypted (asdcplib-rs AesDecContext; key from a dcpwizard KEYS.json image key or a raw hex key; encrypted-with-no-key fails loud), decodes the J2K in process with grok to raw X'Y'Z' codes and colour-manages them to sRGB or a monitor ICC. `render_dcp_frame` writes one colour-correct still, as a binary PPM itself or any other format through ffmpeg; `play_dcp` decodes a range into a lossless intermediate and plays it. `extract_frame` routes to this path when its input is a picture MXF whose codestream declares a DCI cinema profile, taking an optional content key (`resolve_picture_key` builds one from raw hex or a KEYS.json entry matched on the picture's asset UUID) and reading that profile from the decrypted codestream, since a frame read without its key is ciphertext; encrypted essence never falls back to ffmpeg, which cannot decrypt it. A codestream declaring an IMF profile takes `render_imf_frame` instead: the AS-02 reader (the AS-DCP one opens an AS-02 file and then fails every `read_frame`), the same grok decode and decrypt, and then the RGB samples straight to 8-bit sRGB, which is what Rec.709 needs and nothing else does. The colour comes off the essence descriptor's ColorPrimaries and TransferCharacteristic; ST 2084, BT.2020, P3-D65 and any UL it does not know are refused by name, and a descriptor that signals nothing warns and is taken as Rec.709, because packages exist that signal nothing. Everything else, broadcast and unrestricted codestreams included, still decodes with ffmpeg. Not real-time (CPU decode, decode-to-intermediate first)
- dolby_vision: HDR10 injection re-encodes with libx265 to write real SEI (copy cannot); RPU work delegates to dovi_tool
- loudness: EBU R128 via loudnorm, with short-term max from a second ebur128 pass
- grok_decoder (feature `grok-ffi`): in-process JPEG 2000 decoding. `decode(codestream, reduce)` takes the bytes, hands grok a buffer stream so nothing touches disk and no process is spawned, and returns planar samples; `reduce` discards that many highest resolution levels, halving each dimension per level, which is all a thumbnail or a black-frame test needs. Two things about grok's output are read off the component rather than assumed, because both are silently wrong pictures otherwise: samples come back at the width the codestream needs (16-bit for a 12-bit picture, not the 32-bit `int32` suggests) and rows carry a stride that need not equal the width. `DecodedFrame::to_xyz12le` packs them into the layout `colour.rs` reads, each 12-bit sample in the high bits of a little-endian 16-bit word. Subsampled, signed and float components are refused by name, since a DCP picture is none of those. Without the feature every call refuses rather than falling back to ffmpeg: that decoder manages a few frames a second at DCP bitrates, which reads as a hang. The correctness gate is a reversible round trip through `grok_encoder`, which is lossless, so the samples that come back must be the samples that went in
- picture_findings: black and frozen runs from ffmpeg's blackdetect and freezedetect, at their own defaults, as inclusive frame intervals. `detection_filters` is the one place the thresholds are written: an encode runs them on a `split` branch of its decode through `with_detection_branch`, and `detect_in_essence` runs them over a finished picture file for a package this process did not encode. Both parse the same stderr through `parse_ffmpeg_stderr`, and both report a run that reaches the last frame, which freezedetect never closes, using the frame count instead. `detect_in_essence` returns an error naming the reason when ffmpeg cannot read the file, because empty findings would read as clean; encrypted essence is the caller's to refuse, since ffmpeg cannot decrypt AS-DCP
- trailer: ratings card and leader are concatenated ahead of the content; output is a media file, no CPL/DCP is produced
- watermark: visible drawtext mark only, not forensic
- composition_timeline: a package directory to the one mpv source that plays its whole composition, resolved ASSETMAP → first CPL in ASSETMAP order → each reel's MainPicture (DCP) or each MainImageSequence resource's TrackFileId (IMF). Several picture files become one `edl://` virtual timeline so duration is the composition total and a seek crosses reel boundaries; one whole-file reel stays a plain path; anything unresolvable leaves both `load_package_dir` callers on the filename/size guess. A reel the CPL enters late or leaves early carries `,start,length` seconds on its EDL segment, converted from edit units with the segment's EditRate, so a trimmed reel plays the span the composition states and nothing more. The CPL's ContentTitleText or ContentTitle rides along as the title both players force into mpv, and `get_metadata` reports `media-title`, so the transport bar names the composition
- mpv_render (feature `libmpv`): in-process playback through libmpv's render API, which is what an embedded preview needs on Wayland, where no process can reparent another's window. The caller drives the drawing: `render_opengl` into its own framebuffer on the thread the GL context belongs to, or `render_software` into an RGBA buffer for tests and screenshots. Everything else is callable from any thread, and must be: the OpenGL context is created with `MPV_RENDER_PARAM_ADVANCED_CONTROL`, so a call that waits on the core deadlocks when it comes from the render thread. `vd-lavc-dr=no` closes the other half of that trap, where the core waits on the render thread for the decoder's buffers. `set_osd_overlay` draws ASS over the video through mpv's `osd-overlay` command, which is how vector QC guides get composited without a video filter touching a frame; the PlayRes canvas an `OsdAssOverlay` names is stretched over the whole rendered surface, bars included, so placing a drawing on the picture is the caller's arithmetic
- burnin: an ffmpeg `subtitles` or `drawtext` overlay written to a video file, for a review copy rather than a package. The styling options reach the `subtitles` filter as ASS `force_style` overrides, and `video_codec`/`video_crf` become `-c:v` and `-crf`, so a burn can be lossless instead of taking the encoder and quality ffmpeg guesses from the output file name. `ffmpeg_args` builds the command line on its own so a test reads it without encoding. Subtitle XML is refused by name, since ffmpeg has no reader for it
- probe, mpv

Audio DSP (pure PCM, no ffmpeg):
- mid_side: M/S to L/R decode in place (L=M+S, R=M-S with DoM's /2 normalization), leaving every other channel byte-identical
- upmix: stereo to 5.1, mirroring DoM's two upmixers (A splits by band through blackman-windowed sinc FIR filters, B is passthrough L/R with a summed centre, lowpassed LFE, and a 20 ms-delayed L-R to both surrounds). Interleaved f32 or stereo-WAV in, 6-channel DCP order L,R,C,LFE,Ls,Rs out
- crossfade: equal-power (cos/sin) join of two PCM sources by frame or by WAV file, failing loud on sample-rate/bit-depth/format/channel mismatch or an overlap longer than either source
- audio_mix_matrix: any input channel to any output channel with a per-cell gain (DoM's audio mapping), the wizards' `--audio-map` flag and matrix widget, with only the lane names a caller answers to left to the caller. `MixMatrix::parse`/`to_spec` define the shared `IN:OUT@GAIN` grammar once (1-based channel numbers, decibels, several inputs summing into one output), `parse_named_audio_map` walks that grammar with a `LaneVocabulary`'s lane names accepted wherever an output channel number is and its own rule turning the highest destination into an output channel count, and `mix_wav_files` streams any number of WAVs frame by frame into one output, concatenating their channels, padding a short input with silence, mixing in f64 with rounding and clamping for integer output and counting clipped samples, so a pure routing (one input per output at 0 dB) reproduces its source samples bit for bit at every depth including 32-bit int and float

Workflow and infra:
- dashboard, version_tracker: sqlite version/delivery DBs
- job_queue: in-memory job store (caller drives execution)
- gui_job_queue: the queue of builds a wizard GUI runs, one job at a time, with its on-disk record. Both wizards' Jobs panels are this type: `GuiJobQueue<C>` over whatever the wizard calls its job config, which implements `GuiJob` to give the queue the only three things it reads (id, title, output_dir) and the serde bounds to write the config to the file. `submit` records the job Queued and queues it, the worker `take_next`/`start`/`finish`es it, and `record` appends one JSON line per state change to `gui-jobs.jsonl`, so the queue survives the window closing: `load_jobs_file` puts what was left Queued back in the queue, fails what was left Running with `INTERRUPTED_MESSAGE`, rewrites the file with one line per job, and sets the next id past the highest restored one so a new build cannot reuse it. `snapshot` is the panel's list, running job first, then queued, then finished newest first, with the same status words the daemon's `batch list` prints. `is_building_into` refuses a second build into a folder a running or queued job already writes to. `jobs_path` takes the env variable name and the data dir from the wizard, because postkit does not know either wizard's name. Nothing here is tauri: the wizards keep the `#[tauri::command]` wrappers and call these methods
- hints: the advisory findings a job raises before an encode, for the rules that hold whatever the package is: a sound peak above -3 dBTP, sound with no language, and per cue file a first subtitle before 4 s, a cue under 15 frames, a gap under 2 frames or an overlap, more than 3 lines, and a line over 52 characters (replaced by the stronger hint at 79). A rule is a `CueRule` over one cue and what surrounds it, read with `first_offence`, which speaks once for the whole job naming the file and the first offending cue's time. Both wizards call this and add their own format's rules over the same types
- preflight: the refusals both wizards make before the encode. `check_burn_supported` is the four a burnt-in subtitle can hit (the file is not there, it is also a timed-text track, the picture is J2K, the frames reach the encoder as X'Y'Z' already), and `BurnTarget.frames_already_xyz` carries the caller's own flag names so the refusal tells a DCP user about `--hdr-already-pq` and an IMF user about `--hdr`
- rest_api: minimal blocking HTTP server
- plugin, watch, webhook, preferences, profiles, report, accessibility, shell_completion
- tms (feature `tms`, off by default): push a written package to a theatre management system over ftp or sftp, DCP-o-matic's `tms_protocol`/`tms_ip`/`tms_path`/`tms_user`/`tms_password` config keys. Every file under the package directory is put into `<path>/<package dir name>/`, remote directories created before the files that go in them, and the first failure stops the upload naming the file and the remote path it was going to. Protocol handling sits behind one `TmsTransport` trait (`ensure_dir`, `put_file`) with an ssh2/libssh2 implementation, a suppaftp one, and a fake the layout tests drive, so nothing in the test run touches a network. sftp checks the host key against `~/.ssh/known_hosts` and refuses an unknown or changed key, printing the SHA256 fingerprint and the `ssh-keyscan` line that would record it: libssh2 verifies nothing by itself, so without that the password goes to whatever answers on the address. ftp warns that the login and the package cross the network in the clear. `TmsConfig` deserializes the config and redacts the password in Debug, and `validate` refuses one naming no server or no login; reading the file is the app's job, both because the path carries the app's name and because a `toml` dependency here would put winnow's `AsRef` impls in front of every crate that links postkit, which stops dcpdoctor's schema reader compiling. The feature is off by default because ssh2 links libssh2 and openssl, which dcpdoctor's wasm build cannot have
